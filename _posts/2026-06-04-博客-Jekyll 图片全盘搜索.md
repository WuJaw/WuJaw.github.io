文章里的图片散落在桌面、下载、截图文件夹里，每次 push 前要手动拖到 `assets/`，忘了就 404。把图片搜索从"项目内随便找找"升级到"Everything 全盘秒搜"，顺便把文章里教学示例的假图片引用也跳过了。

---

## 1. 五层搜索策略

脚本按以下优先级逐层查找图片，找到即停：

| 层级 | 搜索范围 | 方法 | 速度 |
|------|---------|------|------|
| ① | `assets/` 目录 | 直接 `isfile` | 瞬间 |
| ② | 项目目录（排除 `.git`、`_site`） | `os.walk` | 快 |
| ③ | 桌面、下载、图片、文档 | `os.walk` | 几秒 |
| ④ | 全盘 | Everything `es.exe` | 秒级 |
| ⑤ | 全盘兜底 | `os.walk` ~ 目录 | 分钟级 |

实际使用中 95% 的图片在第 ① 层就命中了（Typora 配置了自动复制到 `assets/`），剩下 5% 靠第 ③ 层在常用目录找到。第 ④⑤ 层是兜底，几乎用不到但放着安心。

## 2. Everything + es.exe 全盘秒搜

[Everything](https://www.voidtools.com/) 是 Windows 上最快的文件搜索工具，维护一个全盘文件名索引（类似 `locate` 但实时更新）。`es.exe` 是它的命令行接口，通过 IPC 和 Everything 后台服务通信，搜索全盘文件只需几十毫秒。

### 2.1. 安装

两个文件缺一不可：

- **Everything 本体**：去 [voidtools.com](https://www.voidtools.com/) 下载安装，安装后会自动在后台建立索引
- **`es.exe`**：Everything 安装目录里自带，也可以从 [voidtools.com/downloads](https://www.voidtools.com/downloads/) 单独下载

为了方便别人快速搭建，我把 `es.exe` 放在项目的 `tools/` 目录里：

```
WuJaw.github.io/
├── tools/
│   ├── es.exe              ← Everything 命令行工具
│   ├── efr32容量剩余计算.html
│   └── CRC16校验工具.html
├── python/
│   ├── fix_img_path.py     ← 含 Everything 搜索逻辑
│   └── ...
```

复用到其他工程时，把整个 `tools/` 和 `python/` 拷过去就行。

### 2.2. es.exe 在脚本里的查找顺序

脚本 `_find_es()` 按以下顺序自动探测 es.exe：

1. **PATH**：`shutil.which('es')` —— 如果已添加到系统 PATH
2. **`python/es.exe`**：兼容旧位置
3. **`tools/es.exe`**：推荐位置
4. **Everything 安装目录**：`Program Files\Everything\` 及其子目录

### 2.3. 调用方式

```python
subprocess.run(
    [es, '-n', '1', '-full-path-and-name', filename],
    capture_output=True, text=True, timeout=5,
)
```

关键参数：

- `-n 1`：只返回第一个结果（同名文件取最近的一个就够了）
- `-full-path-and-name`：输出完整绝对路径（**不能**用 `-name`，下面讲踩坑）
- `timeout=5`：5 秒超时，防止 Everything 服务没响应时卡死

### 2.4. 踩坑：`-name` vs `-full-path-and-name`

最初用的是 `-name` 参数，觉得"按文件名搜索"语义更准确：

```
es.exe -n 1 -name screenshot.png
→ screenshot.png
```

输出只有裸文件名，没有路径。`os.path.isfile("screenshot.png")` 在当前工作目录找不到，永远返回 `None`。

改为 `-full-path-and-name`：

```
es.exe -n 1 -full-path-and-name screenshot.png
→ C:\Users\wuergou\Desktop\screenshot.png
```

输出完整路径，`os.path.isfile` 正确匹配。

注意 `-full-path-and-name` 不加 `-name` 时匹配范围略宽（路径中任意位置出现文件名都匹配），但后续 `os.path.isfile` 能兜底过滤掉目录名误匹配。

### 2.5. Windows GUI vs 命令行

一个常见困惑：Everything 图形界面能搜到，但脚本找不到。可能的原因：

1. **es.exe 没放在正确位置**：脚本只在上述 4 个路径查找
2. **Everything 服务没运行**：`es.exe` 依赖 Everything 后台服务，`tasklist | findstr Everything` 确认进程在跑
3. **用了 `-name` 而非 `-full-path-and-name`**：前面讲过的坑

## 3. 代码块保护：围栏 + 行内

博客文章里经常展示图片写法的教学示例，这些不是真实图片不能被处理。

### 3.1. 围栏代码块（` ``` `）

第一层保护：按 ` ``` ` 分割文件，代码块内的内容原样保留。

### 3.2. 行内代码（`` ` ``）

第二层保护：在非代码块段落中，再按行内代码分割，跳过单反引号包裹的内容。

```
- Typora 写作时路径为 `![desc](../assets/xxx.png)`  ← 行内代码，跳过
- 真实图片 ![截图](../assets/screenshot.png)        ← 正常处理
```

实现上有个坑：fence 分割后，每个非代码 chunk 都以 ` ``` ` 行开头（上一个代码块的关闭标记）。如果直接用 `INLINE_CODE` 匹配整个 chunk，` ``` ` 里的反引号会干扰行内代码边界：

```
```               ← 残留的关闭 fence
                  ← 空行
- 路径为 `![desc](../assets/xxx.png)`
```

INLINE_CODE 贪婪匹配会把 `` ` `` 和 ` ``` ` 的第三个反引号配对，导致教学示例落在"行内代码外"被错误处理。

修复方式：处理 chunk 前先用 `LEADING_FENCE` 正则（`^```[^\n]*\n`）匹配并临时去掉开头的 fence 行，处理完再放回去：

```python
LEADING_FENCE = re.compile(r'^```[^\n]*\n')

maybe_fence = ''
fm = LEADING_FENCE.match(chunk)
if fm:
    maybe_fence = fm.group()
    chunk = chunk[fm.end():]

chunk = _process_chunk(chunk)         # 安全处理
chunk = maybe_fence + chunk           # 放回 fence 行
```

## 复用到其他项目

1. 拷贝 `python/` 和 `tools/` 两个目录到目标工程根目录
2. 安装 [Everything](https://www.voidtools.com/)（可选但推荐，没有也不影响脚本运行，只是兜底搜索慢一些）
3. `python` 命令可用即可，脚本只用标准库，零依赖

Everything 装与不装的区别：装了秒搜全盘，不装降到 `os.walk` 兜底（会在用户目录遍历，大约需要几十秒到几分钟）。
